# 2026-09-04 H100 训练提速 A/B（earbuds 0904 配置）

**机器**：ebcloud 8×H100 80GB，hb-openpi 环境（jax 0.5.3，cuDNN 9.19）
**配置**：`configs/_examples/pi05_base_bi_flexiv_earbuds_case_insertion_teleop_rtc_0904_h100.yaml`
（pi05、cuDNN fp16 attention、batch_image_views、全局 batch 256、64 workers、fsdp 8）
**数据**：`Xense/earbud_case_insertion_teleop_0515_left_right`，776 集 / 1,145,613 帧

> 注：实验当天远端机器的 localstorage 随后被清空，本文与相关代码是事后在本机重建并提交的；

## 口径

每个变体从 pi05_base 权重起跑 400 步，`strict_batch_order: true`，关 checkpoint 和 W&B，
其余与生产配置相同（短跑用一份复制自生产 yaml 的临时 config，CLI 覆盖单个变量）。
主指标是日志里 `Step 100` 到 `Step 300` 两条时间戳之差除以 200，即含日志开销的端到端墙钟 s/step。
step 300 的 loss 用来确认数值没变。

## 各项说明

### E1：token 长度按数据集实测收紧

`scripts/token_len_scan.py` 走真实 transform 链（repack → BiFlexivInputs → Normalize →
TokenizePrompt），对 4037 个状态（含每一维的最小/最大值样本）做 tokenize：min 110、p50 113、p99 115、
**max 116**。原来 200 里有 84 个是纯 padding，但 attention/MLP 照算。128 留 12 个余量。
换数据集或改 prompt 时必须重扫；tokenizer 超长会 warning 并截断，不会报错。

```bash
JAX_PLATFORMS=cpu uv run scripts/token_len_scan.py \
  --config-name pi05_base_bi_flexiv_earbuds_case_insertion_teleop_rtc_0904_h100
```

### E3：XLA 标志

```
--xla_gpu_enable_latency_hiding_scheduler=true
--xla_gpu_all_gather_combine_threshold_bytes=1073741824
--xla_gpu_reduce_scatter_combine_threshold_bytes=1073741824
--xla_gpu_all_reduce_combine_threshold_bytes=1073741824
--xla_gpu_enable_pipelined_all_gather=true
--xla_gpu_enable_pipelined_reduce_scatter=true
--xla_gpu_enable_while_loop_double_buffering=true
```

FSDP 每步的参数 all-gather / 梯度 reduce-scatter 合并成大块并与计算流水。没有逐项拆分测哪一个起作用。
通过 `XLA_FLAGS` 环境变量传入，已写在 0904 yaml 头部注释里。

### E2：remat 在 80 GB 上没有空间

`gemma.py` / `siglip.py` 每层用 `nothing_saveable` 全量重算。本次给 `Pi0Config` 加了
`gemma_remat_policy` / `siglip_remat_policy`（默认不变），并在 cuDNN 调用前给 q/k/v/mask 加了统一的
batch 分片约束（`gemma.py`，否则非默认 remat 策略下编译失败）。但 batch 256（每卡 32）时：
完全不 remat 要 280 GiB 单块，只保存无 batch 维 matmul 也要 84.6 GB，都放不下。
在 H200 141 GB 或每卡 batch 更小时这两个开关才可能兑现，理论上限约为一次前向的重算（15–25%）。

### 其他观察

- 数据侧：等数据 0.03–0.04 s/step，64 workers 足够；worker 启动一次约 330 s（spawn 上下文，64 进程各自
  import jax/torch/lerobot 并反序列化 1.1M 行数据集），是每次启动的一次性开销。
- `ResizeImages` 实际调用的是 `xense_client.image_tools`（PIL），worker 里不跑 JAX resize。
- fsdp 4 相对 8 没有收益：参数 all-gather 的量只差 12.5%，而每卡持有的优化器状态翻倍。
- 短跑结束后偶有 DataLoader worker 成为孤儿进程（ppid 1，每个约 3 GB RSS），一次残留了 39 个；
  跑完批量实验后用 `ps -eo pid,ppid,cmd | grep spawn_main` 检查一下。
- 该配置 `num_train_steps: 60000` 但 `lr_schedule.decay_steps` 仍是默认 30000，后半程一直在底线 LR；
  这是训练质量问题，本次未动。
